# 为什么要用MVVM

### 一、MVC（Model-View-Controller）

#### 核心定义

MVC 是最早出现的经典架构模式，将应用分为三个核心部分：

- Model（模型）：处理数据逻辑和业务规则，负责数据的存储、获取和处理，不依赖于视图和控制器。
- View（视图）：展示数据，是用户界面（如页面、表单），依赖于模型的数据更新。
- Controller（控制器）：接收用户输入，协调模型和视图，根据输入调用模型处理数据，再通知视图更新。

#### 优点

1. 关注点分离：模型、视图、控制器职责明确，降低代码耦合度，便于团队分工开发（如前端开发者负责视图，后端开发者负责模型）。
2. 复用性强：同一模型可对应多个视图（如一份数据既可以用表格展示，也可以用图表展示）。
3. 灵活性高：视图和模型分离，修改视图（如 UI 样式）不会影响模型，反之亦然。

#### 缺点

1. 视图与模型存在间接依赖：虽然视图不直接操作模型，但视图需要依赖模型的数据结构，当模型数据结构变化时，视图可能需要调整。
2. 控制器职责可能过重：复杂业务中，控制器可能会处理大量逻辑，导致 “胖控制器” 问题，难以维护。
3. 测试难度较高：视图通常与用户交互紧密，单元测试时可能需要模拟大量用户输入场景。

#### 适用场景

- 早期桌面应用、传统 Web 应用（如 Java EE 的 Struts 框架）。
- 业务逻辑相对简单、视图与模型交互不频繁的场景。

### 二、MVP（Model-View-Presenter）

#### 核心定义

MVP 是 MVC 的衍生模式，旨在解决 MVC 中视图与模型的依赖问题，核心改进是引入 Presenter（Presenter） 替代 Controller：

- Model（模型）：与 MVC 中的模型一致，处理数据逻辑。
- View（视图）：仅负责展示和接收用户输入，不直接依赖模型，通过 Presenter 与模型交互。
- Presenter（Presenter）：作为视图和模型的中间层，完全隔离视图和模型，接收视图的用户输入，调用模型处理数据，再将结果返回给视图并驱动视图更新。

#### 优点

1. 完全解耦视图与模型：视图仅通过 Presenter 与模型交互，不依赖模型的数据结构，模型变化时视图无需修改，降低耦合度。
2. 便于单元测试：Presenter 不依赖具体视图（可通过接口定义视图），可通过模拟视图和模型对 Presenter 进行独立测试。
3. 视图职责更单一：视图仅负责 UI 展示，不包含业务逻辑，代码更简洁。

#### 缺点

1. Presenter 与视图绑定紧密：Presenter 需要处理视图的所有交互逻辑，当视图复杂时，Presenter 可能变得臃肿（“胖 Presenter”）。
2. 视图的复用性降低：视图依赖于 Presenter 的接口，若更换 Presenter，视图可能需要调整。
3. 实现成本较高：相比 MVC，需要定义更多接口（如视图接口、模型接口），初期开发效率可能较低。

#### 适用场景

- 桌面应用和移动应用（如 Android 的早期架构）。
- 对测试要求高、视图与模型需要完全解耦的场景（如金融、医疗等领域的应用，需严格保证逻辑正确性）。

### 三、MVVM（Model-View-ViewModel）

#### 核心定义

MVVM 是为应对现代前端框架（如 Vue、React）的双向绑定需求而设计的模式，核心是 ViewModel（ViewModel）：

- Model（模型）：与前两种模式一致，处理数据逻辑。
- View（视图）：用户界面，通过数据绑定与 ViewModel 关联，自动响应 ViewModel 的数据变化。
- ViewModel（ViewModel）：连接视图和模型的桥梁，包含视图所需的数据和命令（如用户操作的处理方法），通过数据绑定实现与视图的双向通信（视图变化自动更新 ViewModel，ViewModel 变化自动更新视图）。

#### 优点

1. 双向数据绑定：视图与 ViewModel 自动同步，减少手动操作 DOM 的代码（如 Vue 的`v-model`、Angular 的`[(ngModel)]`），开发效率高。
2. 低耦合：视图与模型完全隔离，ViewModel 不依赖视图，便于测试和复用。
3. 职责清晰：ViewModel 专注于处理视图所需的数据和逻辑，视图仅负责展示，模型专注于业务规则。

#### 缺点

1. 调试难度增加：双向绑定可能导致数据变化来源不明确，排查问题时需要跟踪 ViewModel 和视图的联动关系。
2. 性能开销：复杂视图中，频繁的数据绑定可能导致性能损耗（如大量列表渲染时）。
3. ViewModel 逻辑可能复杂：当视图交互复杂时，ViewModel 需处理大量数据转换和事件响应，可能变得臃肿。

#### 适用场景

- 现代前端框架（如 Vue、React、Angular）、移动应用（如 Flutter）。
- 视图与数据交互频繁、需要快速响应 UI 变化的场景（如表单提交、实时数据展示）。

## 总结

- MVC 是基础架构，适合简单场景，但视图与模型存在依赖，控制器易臃肿。
- MVP 强化了解耦，适合对测试和隔离性要求高的场景，但 Presenter 可能复杂。
- MVVM 借助双向绑定提升开发效率，适合现代前端和交互频繁的应用，但需注意性能和调试问题。

选择架构时需结合业务复杂度、团队技术栈和测试需求：简单场景用 MVC，高隔离性需求用 MVP，前端交互复杂用 MVVM。
