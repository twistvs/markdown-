# UE5 面试题出题标准

本标准供本项目后续出题时参考。用户在具体请求中指定的范围、数量或格式优先于本标准。

## 一、面向的候选人

- 正在参加秋招的硕士应届生，目标为 UE5 开发岗位。
- 实习主要从事 UE5 系统开发，重点为 UI 交互开发。
- 实习项目采用 Mass 数据架构、CommonUI UI 架构，并通过 MVVM 驱动 UI 表现。
- 可以结合上述经历设计问题，但不得假设候选人做过未说明的功能或拥有未说明的项目成果。

## 二、题目选择

- 优先覆盖岗位常见考点、核心概念、基本原理和实际开发中容易出错的环节。
- 按用户指定主题出题。基础题以通用 UE5 知识为主；UI、Mass、CommonUI、MVVM 专题再深入相应框架。
- 题目应适合应届生回答，兼顾概念理解与实际运用；避免以冷门 API、源码行号或死记细节作为主要考点。
- 每题聚焦一个核心问题，必要时附带一个紧密相关的追问；避免把多个独立考点堆在同一道题中。
- 不重复或仅换措辞重复同一问题。优先采用“是什么、有什么区别、为什么、如何选择、如何排查”等清晰问法。
- 不将主观经验包装为确定的考察概率；若无可靠统计，使用“常见考点”“优先准备”等表述。

## 三、参考答案：尽可能简短

- **默认每道题都必须附参考答案**，除非用户明确要求只出题。
- 先直接回答核心问题，再补充理解该问题必需的区别、原因或条件；不重复题干，不写无关背景。
- 概念题通常用 **1–3 句**；比较题或流程题通常用 **2–4 个短要点**。这些是默认目标，不是强制字数上限。
- 题干包含追问时，答案也应简短覆盖追问；若无法简洁回答，应优先缩小题目范围或拆题。
- 保留准确性所需的限定条件，尤其是生命周期、对象所有权、垃圾回收、线程和网络行为；不得为了简短使用错误的绝对化结论。
- 默认不附长篇解释、完整源码或大量例子。只有代码能明显提高理解时，才给出最小必要片段。
- 对受 UE5 版本、插件配置或运行环境影响的结论，简短注明适用条件；不确定的细节应核实或明确说明，不能编造。
- 参考答案定位为面试复习提纲，便于快速回忆和口头表达，不要求完整展开所有实现细节。

## 四、文件与排版

- 将题目输出到本项目根目录的 Markdown 文件中，文件名应体现主题与数量，例如 `UE5基础知识面试题50道.md`。
- 文件开头简短说明适用范围，再按知识主题分组；题目采用全篇连续编号。
- 每题紧接参考答案，避免将全部答案放到文末，减少查阅成本。
- 默认使用中文，保留必要的英文术语和准确的 API 名称。
- 用户指定题数时，按独立题目计数；附带追问不另计题数。
- 不覆盖已有文件中的其他内容。修改现有题库或补充旧题答案，应以用户当前请求为准。

## 五、统一模板

```markdown
# UE5［主题］面试题（N 道）

适用范围：［简短说明］。

## 一、［知识主题］

### 1. ［核心问题；必要时附一个相关追问］

**参考答案：**［直接回答，用 1–3 句概括必要结论。］

### 2. ［比较题或流程题］

**参考答案：**

- ［关键区别或步骤一］
- ［关键区别或步骤二］
```

## 六、简短答案示例

### 示例：`FString`、`FName` 和 `FText` 有什么区别？

**参考答案：**`FString` 用于可操作的字符串；`FName` 用于名称标识和高效比较；`FText` 支持本地化，适合面向用户的显示文本。

## 七、交付前检查

- 题目数量和编号正确，主题符合用户要求，无明显重复。
- 每题都有简短参考答案，答案覆盖题干及附带追问。
- 核心术语和 API 名称准确，必要条件清楚，没有误导性的绝对结论。
- 文件保存在项目根目录，并在回复中提供文件链接。
