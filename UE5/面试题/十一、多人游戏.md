下面回答 **十一、网络同步问题**。实习岗不一定会问得特别深，但如果岗位涉及多人游戏，或者你简历里写了联机、GAS、射击、合作玩法，那么网络同步就是高频考点。

------

# 十一、网络同步问题

UE 的网络系统核心可以先记住一句话：

> UE 多人游戏通常采用客户端-服务器模型，服务器拥有权威状态，客户端负责输入和表现，服务器负责验证和同步结果。

------

# 1. UE 网络模型是什么？

UE 默认使用 **Client-Server** 模型。

也就是说，一局多人游戏中通常有：

```text
Server：服务器，拥有权威状态
Client：客户端，玩家本地机器
```

服务器负责：

```text
生成关键 Actor
处理游戏规则
验证玩家操作
计算真实伤害
同步角色状态
决定胜负
```

客户端负责：

```text
接收玩家输入
本地显示 UI
播放本地表现
向服务器发送请求
接收服务器同步结果
```

比如玩家攻击敌人：

```text
玩家按下攻击键
    ↓
客户端请求服务器攻击
    ↓
服务器验证是否能攻击
    ↓
服务器计算命中和伤害
    ↓
服务器同步敌人血量
    ↓
客户端显示受击、飘字、特效
```

------

## 面试推荐回答

> UE 多人游戏通常是客户端-服务器模型，服务器拥有权威状态。客户端接收玩家输入并向服务器发送请求，服务器验证并执行真正的游戏逻辑，然后把结果同步给客户端。这样可以减少作弊，也能保证所有玩家看到的核心状态一致。

------

# 2. Server Authority 是什么？

`Authority` 可以理解为“谁有权决定这个对象的真实状态”。

在 UE 中，一般是：

```text
服务器拥有 Authority
客户端通常是 Simulated Proxy 或 Autonomous Proxy
```

例如敌人血量：

```text
服务器上的敌人血量 = 真实血量
客户端上的敌人血量 = 服务器同步过来的副本
```

所以多人游戏中不应该让普通客户端直接决定：

```text
敌人是否死亡
是否造成伤害
是否获得金币
是否释放成功
```

这些关键逻辑应该由服务器决定。

------

## C++ 中判断 Authority

```cpp
if (HasAuthority())
{
    // 只在服务器执行
}
```

蓝图中常用：

```text
Switch Has Authority
```

------

## 面试推荐回答

> Authority 表示谁拥有对象状态的决定权。UE 多人游戏中通常服务器拥有 Authority，关键游戏逻辑应该在服务器执行，比如伤害、死亡、拾取、生成物品等。客户端可以请求服务器执行，但不应该直接修改权威状态。

------

# 3. Replication 是什么？

`Replication` 就是**网络复制**。

它的作用是：

> 把服务器上的 Actor 或变量状态同步到客户端。

例如服务器上有一个角色：

```text
Server:
PlayerCharacter.Location = (100, 200, 0)
Health = 80
```

经过复制后，客户端也能看到：

```text
Client:
PlayerCharacter.Location = (100, 200, 0)
Health = 80
```

------

# 4. Actor 如何开启复制？

如果一个 Actor 想同步到客户端，需要开启 Replicates。

蓝图中：

```text
Class Defaults
    → Replicates = true
```

C++ 中：

```cpp
AMyActor::AMyActor()
{
    bReplicates = true;
}
```

如果这个 Actor 还需要同步移动：

```cpp
AMyActor::AMyActor()
{
    bReplicates = true;
    SetReplicateMovement(true);
}
```

------

## 面试推荐回答

> Replication 是服务器把 Actor 或变量状态同步到客户端的机制。Actor 想被同步，首先要开启 Replicates。如果需要同步位置移动，还要开启 Replicate Movement。一般服务器生成的可复制 Actor 会同步到相关客户端。

------

# 5. 变量复制怎么做？

如果想同步变量，比如血量：

```cpp
UPROPERTY(Replicated)
float Health;
```

还需要在 C++ 中注册复制属性：

```cpp
void AMyCharacter::GetLifetimeReplicatedProps(
    TArray<FLifetimeProperty>& OutLifetimeProps
) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);

    DOREPLIFETIME(AMyCharacter, Health);
}
```

蓝图中可以把变量 Replication 设置为：

```text
Replicated
```

或者：

```text
RepNotify
```

------

## 面试推荐回答

> 变量复制是把服务器上的变量值同步到客户端。C++ 中变量需要加 UPROPERTY(Replicated)，并在 GetLifetimeReplicatedProps 中用 DOREPLIFETIME 注册。蓝图中可以直接把变量设置为 Replicated 或 RepNotify。

------

# 6. RepNotify 是什么？

`RepNotify` 是变量复制后的回调。

也就是说：

> 当一个复制变量在客户端收到新值时，会自动调用一个通知函数。

例如血量：

```cpp
UPROPERTY(ReplicatedUsing = OnRep_Health)
float Health;

UFUNCTION()
void OnRep_Health();
```

当服务器修改 Health 并同步到客户端后，客户端会调用：

```cpp
void AMyCharacter::OnRep_Health()
{
    UpdateHealthBar();
    PlayHitEffect();
}
```

------

## RepNotify 适合什么？

适合客户端收到状态变化后做表现：

```text
血量变化 → 更新血条
状态变化 → 更新动画
武器变化 → 刷新模型
队伍变化 → 改变颜色
死亡状态变化 → 播放死亡表现
```

------

## 注意点

服务器修改变量时，服务器自己不一定自动调用 `OnRep`。

所以有时服务器也需要手动执行对应逻辑：

```cpp
Health = NewHealth;
OnRep_Health();
```

或者把表现逻辑拆成一个公共函数。

------

## 面试推荐回答

> RepNotify 是复制变量变化后的回调。当服务器修改变量并同步到客户端后，客户端会执行 OnRep 函数，常用于更新 UI、动画或表现效果。比如 Health 使用 RepNotify，客户端收到新血量后更新血条。

------

# 7. RPC 是什么？

`RPC` 是 Remote Procedure Call，远程过程调用。

简单说：

> RPC 是让某台机器调用另一台机器上的函数。

UE 中常见 RPC 有三类：

```text
Server RPC
Client RPC
Multicast RPC
```

------

# 8. Server RPC 是什么？

`Server RPC` 是客户端请求服务器执行函数。

例如玩家按攻击键：

```text
客户端按下攻击
    ↓
调用 Server_Attack
    ↓
服务器执行真正攻击逻辑
```

C++ 示例：

```cpp
UFUNCTION(Server, Reliable)
void Server_Attack();
```

实现：

```cpp
void AMyCharacter::Server_Attack_Implementation()
{
    // 服务器执行攻击逻辑
}
```

------

## Server RPC 常见用途

```text
请求攻击
请求释放技能
请求拾取物品
请求交互
请求换武器
请求移动相关输入
```

------

## 面试推荐回答

> Server RPC 是客户端请求服务器执行某个函数。比如玩家本地按下攻击键，客户端调用 Server_Attack，服务器验证攻击是否合法并执行伤害逻辑。关键游戏逻辑应该通过 Server RPC 交给服务器处理。

------

# 9. Client RPC 是什么？

`Client RPC` 是服务器调用某个客户端上的函数。

例如：

```text
服务器判断玩家死亡
    ↓
调用 Client_ShowDeathUI
    ↓
该玩家客户端显示死亡界面
```

C++ 示例：

```cpp
UFUNCTION(Client, Reliable)
void Client_ShowDeathUI();
```

------

## Client RPC 常见用途

```text
通知某个玩家打开 UI
显示本地提示
播放只给某个玩家看的效果
通知客户端进入结算界面
返回交互结果
```

------

## 面试推荐回答

> Client RPC 是服务器调用某个客户端上的函数，通常用于只通知某个玩家的表现或 UI，比如显示死亡界面、打开结算面板、显示错误提示等。

------

# 10. Multicast RPC 是什么？

`Multicast RPC` 是服务器调用后，在所有相关客户端都执行的函数。

例如爆炸：

```text
服务器生成爆炸结果
    ↓
调用 Multicast_PlayExplosion
    ↓
所有客户端播放爆炸特效和音效
```

C++ 示例：

```cpp
UFUNCTION(NetMulticast, Unreliable)
void Multicast_PlayExplosionFX();
```

------

## Multicast 常见用途

```text
播放爆炸特效
播放公共音效
播放攻击挥砍特效
播放死亡表现
刷新公共表现
```

------

## 注意点

Multicast 应该由服务器调用才有意义。

如果客户端直接调用 Multicast，一般只会在自己本地执行，不会广播给别人。

------

## 面试推荐回答

> Multicast RPC 是服务器调用后让所有相关客户端都执行的函数，常用于播放所有人都能看到的表现，比如爆炸、死亡、攻击特效。它应该由服务器调用，客户端直接调用不会真正广播给所有人。

------

# 11. Replication 和 RPC 有什么区别？

这是非常高频的问题。

简单区分：

```text
Replication：同步状态
RPC：同步事件
```

------

## 11.1 Replication 适合持续状态

例如：

```text
血量
位置
当前武器
是否死亡
队伍
分数
Buff 状态
```

这些是“现在是什么状态”。

------

## 11.2 RPC 适合瞬时事件

例如：

```text
播放爆炸
播放音效
显示提示
执行一次攻击请求
播放开门动画
```

这些是“发生了一件事”。

------

## 对比表

| 对比                 | Replication      | RPC                |
| -------------------- | ---------------- | ------------------ |
| 作用                 | 同步状态         | 调用远程函数       |
| 适合                 | 血量、位置、分数 | 攻击请求、播放特效 |
| 是否保存状态         | 是               | 否                 |
| 新加入客户端能看到吗 | 可以看到当前状态 | 不会收到过去事件   |

------

## 面试推荐回答

> Replication 更适合同步持续状态，比如血量、分数、是否死亡；RPC 更适合同步瞬时事件，比如攻击请求、播放爆炸特效、打开 UI。简单说，变量复制同步“状态”，RPC 同步“事件”。

------

# 12. Reliable 和 Unreliable 有什么区别？

RPC 可以设置为：

```text
Reliable
Unreliable
```

------

## Reliable

`Reliable` 表示可靠调用，会尽力保证送达，并保持顺序。

适合重要事件：

```text
释放技能请求
拾取物品
购买道具
开门交互
任务完成
```

------

## Unreliable

`Unreliable` 表示不保证一定送达。

适合高频、不重要、可丢失事件：

```text
脚步声
枪口火焰
临时特效
频繁的瞄准方向
非关键表现
```

------

## 注意点

不要把所有 RPC 都设成 Reliable。

如果大量 Reliable RPC 堆积，可能导致网络拥塞，反而影响同步。

------

## 面试推荐回答

> Reliable RPC 会尽力保证送达，适合关键事件，比如释放技能、拾取物品。Unreliable 不保证一定送达，适合高频表现，比如枪口火焰、脚步声、临时特效。不能滥用 Reliable，否则网络拥塞时会造成延迟和堆积。

------

# 13. Owner 是什么？为什么 RPC 有时调用失败？

在 UE 网络中，`Owner` 很重要。

通常：

```text
PlayerController 拥有自己的 Pawn
Pawn 拥有自己的武器
武器可以通过 SetOwner 设置拥有者
```

很多 RPC 有调用权限要求。

例如：

> 客户端想调用某个 Actor 的 Server RPC，通常这个 Actor 需要被该客户端拥有，或者在它的拥有链上。

------

## 常见问题

你在客户端武器 Actor 上调用：

```text
Server_Fire
```

但武器没有正确 Owner，结果 Server RPC 不执行。

解决方式：

```cpp
Weapon->SetOwner(PlayerCharacter);
```

或者让输入先走 Character / PlayerController，再由服务器调用武器逻辑。

------

## 面试推荐回答

> UE 中 RPC 和 Owner 有关系。客户端通常只能在自己拥有的 Actor 上调用 Server RPC，比如自己的 PlayerController、Pawn 或拥有链上的武器。如果 Actor 没有正确设置 Owner，客户端调用 Server RPC 可能不会到服务器。

------

# 14. PlayerController、PlayerState、GameState、GameMode 在网络中有什么区别？

这个问题前面基础部分讲过，这里从网络角度再总结。

| 类               | 服务器                         | 客户端         | 是否适合同步数据      |
| ---------------- | ------------------------------ | -------------- | --------------------- |
| GameMode         | 有                             | 没有           | 不直接给客户端同步    |
| GameState        | 有                             | 有             | 适合同步全局状态      |
| PlayerController | 服务器有，每个客户端只有自己的 | 只拥有自己的   | 适合本地输入和私有 UI |
| PlayerState      | 有                             | 所有客户端都有 | 适合同步玩家公开数据  |

------

## 示例

### 比赛时间

放在：

```text
GameState
```

因为所有客户端都需要知道。

------

### 玩家分数

放在：

```text
PlayerState
```

因为所有人都需要看到每个玩家分数。

------

### 玩家本地背包 UI

放在：

```text
PlayerController / Widget
```

因为只给自己看。

------

### 胜负规则

放在：

```text
GameMode
```

因为服务器决定规则。

------

## 面试推荐回答

> GameMode 只在服务器存在，适合放游戏规则；GameState 存在于服务器和客户端，适合同步全局状态；PlayerController 在客户端通常只有自己的，适合处理输入和本地 UI；PlayerState 会复制给所有客户端，适合同步玩家名字、分数、队伍等公开信息。

------

# 15. 网络中 UI 应该在哪里创建？

UMG UI 一般只在本地客户端创建。

常见位置：

```text
本地 PlayerController
```

不要在 GameMode 中创建 UI，因为：

```text
GameMode 只在服务器存在
客户端没有 GameMode
```

C++ 中可以判断：

```cpp
if (IsLocalController())
{
    // 创建 UI
}
```

蓝图中也要确保是本地玩家控制器创建。

------

## 面试推荐回答

> 多人游戏中 UI 一般只在本地客户端创建，常放在本地 PlayerController 中。不要在 GameMode 创建 UI，因为 GameMode 只在服务器存在。需要显示的数据可以通过复制变量、RepNotify 或 Client RPC 通知本地 UI 更新。

------

# 16. 客户端能不能直接修改血量？

不应该。

错误做法：

```text
客户端命中敌人
    ↓
直接 Enemy.Health -= 20
```

这样有几个问题：

```text
容易作弊
其他客户端不同步
服务器状态不一致
```

正确做法：

```text
客户端请求攻击
    ↓
Server RPC
    ↓
服务器验证命中
    ↓
服务器修改敌人 Health
    ↓
Health 复制到客户端
```

------

## 面试推荐回答

> 客户端不应该直接修改血量这类权威状态。客户端可以请求攻击，但服务器应该验证命中并修改 Health，然后通过 Replication 或 RepNotify 同步给客户端。这样能保证状态一致并减少作弊。

------

# 17. 如何同步血量 UI？

常见做法：

```text
服务器修改 Health
    ↓
Health 使用 RepNotify 同步到客户端
    ↓
OnRep_Health 更新本地 UI
```

例如：

```cpp
UPROPERTY(ReplicatedUsing = OnRep_Health)
float Health;

void AMyCharacter::OnRep_Health()
{
    OnHealthChanged.Broadcast(Health, MaxHealth);
}
```

UI 绑定 `OnHealthChanged` 更新血条。

------

## 面试推荐回答

> 多人游戏中血量应该由服务器修改，并用 RepNotify 同步到客户端。客户端收到 OnRep_Health 后，可以广播 OnHealthChanged 事件，让 UI 更新血条。这样 UI 显示来自服务器权威状态。

------

# 18. 如何同步攻击动画？

攻击动画可以有几种方案。

------

## 方案一：Replicated 变量驱动

服务器设置：

```text
bIsAttacking = true
```

客户端 OnRep 后播放动画。

适合状态型动画，但对一次性动画要小心重复触发。

------

## 方案二：Multicast RPC 播放 Montage

```text
客户端按攻击
    ↓
Server_Attack
    ↓
服务器验证
    ↓
Multicast_PlayAttackMontage
    ↓
所有客户端播放攻击 Montage
```

适合所有人都要看到的一次性攻击动画。

------

## 方案三：GAS Montage 复制

如果使用 GAS，可以利用 GAS 的 Ability 和 Montage 复制机制，处理会更体系化。

------

## 面试推荐回答

> 攻击动画可以通过服务器验证后 Multicast 播放 Montage，让所有客户端看到攻击表现。也可以用 RepNotify 状态变量驱动动画。对于一次性动作，Multicast 比单纯复制 bool 更直观；如果项目用 GAS，可以通过 Ability 的 Montage 复制机制处理。

------

# 19. 如何同步子弹？

子弹分两类：Hit Scan 和 Projectile。

------

## 19.1 Hit Scan 武器

比如步枪、手枪。

常见做法：

```text
客户端开火输入
    ↓
Server_Fire
    ↓
服务器做 Line Trace 或验证命中
    ↓
服务器应用伤害
    ↓
Multicast 播放枪口火焰、弹道、命中特效
```

为了手感，也可以客户端先本地播放枪口火焰，再等服务器结果。

------

## 19.2 Projectile 子弹

比如火箭弹、魔法球。

常见做法：

```text
客户端请求发射
    ↓
服务器 SpawnActor Projectile
    ↓
Projectile 开启 Replicates
    ↓
客户端看到同步出来的 Projectile
    ↓
服务器处理命中和伤害
```

------

## 面试推荐回答

> Hit Scan 武器通常通过 Server RPC 请求开火，服务器做命中检测和伤害，再 Multicast 播放表现。Projectile 武器通常由服务器 Spawn 可复制的 Projectile Actor，让它同步到客户端，命中和伤害由服务器处理。

------

# 20. 网络中 SpawnActor 应该在哪执行？

需要同步给所有人的关键 Actor，应该由服务器生成。

例如：

```text
敌人
拾取物
Projectile
可交互物
掉落物
```

应该：

```cpp
if (HasAuthority())
{
    GetWorld()->SpawnActor<AProjectile>(ProjectileClass, Location, Rotation);
}
```

并确保 Actor：

```cpp
bReplicates = true;
```

------

## 客户端 Spawn 会怎样？

如果客户端本地 Spawn 一个普通 Actor：

```text
只有自己看得到
服务器和其他客户端不知道
```

适合纯本地表现：

```text
本地 UI
本地临时特效
本地预测表现
```

但不适合权威游戏对象。

------

## 面试推荐回答

> 需要所有人看到、并参与游戏逻辑的 Actor 应该由服务器 Spawn，并开启 Replicates。客户端本地 Spawn 的 Actor 通常只在自己机器上存在，适合纯表现或预测，不适合敌人、掉落物、Projectile 这类权威对象。

------

# 21. 网络相关性 Relevancy 是什么？

服务器不一定把所有 Actor 都同步给所有客户端。

`Relevancy` 可以理解为：

> 这个 Actor 对某个客户端是否相关，是否需要同步给它。

例如：

```text
离玩家很远的敌人
另一个区域的掉落物
看不见也无交互的物体
```

可以降低同步频率或不同步。

常见优化字段：

```text
Net Cull Distance
Net Update Frequency
Only Relevant to Owner
Always Relevant
```

------

## 面试推荐回答

> 网络相关性决定 Actor 是否需要同步给某个客户端。远离玩家或无关的 Actor 可以不频繁同步，从而减少网络带宽。UE 可以通过 Net Cull Distance、Net Update Frequency、Only Relevant to Owner 等设置优化网络复制。

------

# 22. Net Update Frequency 是什么？

`Net Update Frequency` 表示 Actor 每秒尝试同步多少次。

例如：

```text
Net Update Frequency = 100
```

表示较高频率同步。

对于不需要高频更新的对象，可以降低：

```text
Net Update Frequency = 5
```

例如：

```text
远处 NPC
低频状态物体
不频繁变化的道具
```

------

## 面试推荐回答

> Net Update Frequency 控制 Actor 网络更新频率。频率越高同步越及时，但带宽和性能开销越大。不重要或变化慢的 Actor 可以降低频率，重要角色和高速运动对象则需要更高频率。

------

# 23. Dormancy 网络休眠是什么？

`Dormancy` 表示 Actor 暂时不需要同步，因为它状态不变。

适合：

```text
关闭的门
静止道具
已经生成但长时间不变化的物体
```

当状态变化时再唤醒同步。

------

## 面试推荐回答

> Dormancy 是网络休眠机制，适合状态长期不变的 Actor。休眠后 Actor 不会频繁复制，节省带宽；当它状态变化时再唤醒同步，比如门从关闭变为打开。

------

# 24. 多人游戏中移动是怎么同步的？

`CharacterMovementComponent` 已经内置了较完整的网络移动同步和预测。

大致流程：

```text
客户端输入移动
    ↓
客户端本地预测移动
    ↓
发送移动输入到服务器
    ↓
服务器验证并修正
    ↓
客户端根据服务器结果校正
```

所以一般角色移动不要自己简单复制位置，而是使用 UE 的 CharacterMovement。

------

## 面试推荐回答

> UE 的 CharacterMovementComponent 内置了客户端预测和服务器校正。客户端输入后会本地预测移动，同时把移动请求发给服务器，服务器验证并回传修正。普通 Character 移动一般不需要手动复制位置，应该使用引擎自带移动组件。

------

# 25. Client Prediction 是什么？

客户端预测是为了降低延迟感。

如果没有预测：

```text
玩家按 W
    ↓
等待服务器确认
    ↓
角色才移动
```

会感觉很卡。

有预测后：

```text
玩家按 W
    ↓
客户端立即移动
    ↓
同时发送给服务器
    ↓
服务器确认或修正
```

------

## 面试推荐回答

> Client Prediction 是客户端预测，为了让玩家操作更流畅。客户端收到输入后先本地执行移动或表现，同时把请求发给服务器，服务器验证后再校正。如果没有预测，玩家每个操作都要等服务器返回，会感觉延迟很大。

------

# 26. Listen Server 和 Dedicated Server 区别

## Listen Server

一个玩家既是服务器又是客户端。

```text
房主开房
房主机器同时运行服务器和本地客户端
```

优点：

```text
简单
适合小型联机
不需要专门服务器
```

缺点：

```text
房主有优势
房主退出游戏可能结束
性能和网络受房主影响
```

------

## Dedicated Server

专用服务器，没有本地玩家画面。

优点：

```text
更公平
更稳定
适合正式多人游戏
```

缺点：

```text
部署成本更高
开发测试更复杂
```

------

## 面试推荐回答

> Listen Server 是玩家主机同时作为服务器和客户端，适合小型联机但房主可能有优势；Dedicated Server 是专用服务器，没有本地玩家画面，更公平稳定，适合正式多人游戏，但部署成本更高。

------

# 27. 常见网络 Bug 排查

## 27.1 客户端看不到 Actor

检查：

```text
Actor 是否服务器生成
bReplicates 是否开启
是否在相关性范围内
是否被隐藏
是否只在本地生成
```

------

## 27.2 RPC 不执行

检查：

```text
RPC 类型是否正确
是否由正确端调用
Actor 是否有 Owner
是否开启复制
函数是否标记 UFUNCTION
是否在服务器/客户端预期对象上调用
```

------

## 27.3 变量不同步

检查：

```text
变量是否 Replicated
是否注册 DOREPLIFETIME
Actor 是否 Replicates
变量是否在服务器修改
客户端是否只改了本地副本
```

------

## 27.4 客户端 UI 不更新

检查：

```text
UI 是否在本地客户端创建
数据是否通过 RepNotify / Delegate 通知
是否试图从 GameMode 读取
PlayerController 是否本地
```

------

## 面试推荐回答

> 网络问题排查时，我会先确认对象是否服务器生成并开启 Replicates；变量是否加 Replicated 并注册 DOREPLIFETIME；RPC 是否从正确端调用，Actor 是否有 Owner；UI 是否只在本地客户端创建。很多问题本质是把服务器逻辑和客户端逻辑混在了一起。

------

# 28. 实战题：多人拾取物怎么实现？

流程：

```text
玩家客户端按 E
    ↓
客户端调用 Server_Interact
    ↓
服务器检查距离、目标是否合法
    ↓
服务器把物品加入玩家背包
    ↓
服务器 Destroy 拾取物
    ↓
背包数据复制或 Client RPC 更新 UI
```

不要让客户端直接 Destroy 物品或加背包。

------

## 面试推荐回答

> 多人拾取中，客户端只能发起请求，真正拾取逻辑由服务器处理。服务器检查玩家距离、物品是否存在、是否可拾取，然后修改玩家背包并销毁物品。背包变化可以通过 RepNotify 或 Client RPC 通知 UI 更新。

------

# 29. 实战题：多人开门怎么实现？

流程：

```text
客户端按 E
    ↓
Server_OpenDoor
    ↓
服务器验证距离和权限
    ↓
服务器设置 bIsOpen = true
    ↓
bIsOpen RepNotify 到客户端
    ↓
OnRep_IsOpen 播放开门动画
```

或者服务器 Multicast 播放动画。

更推荐状态用 RepNotify：

```text
门是否打开是状态
所以用复制变量比较合适
```

------

## 面试推荐回答

> 开门这种逻辑可以让客户端请求服务器，服务器验证后设置门的 bIsOpen 状态，并通过 RepNotify 同步给客户端。客户端在 OnRep_IsOpen 中播放开门动画。因为门是否打开是持续状态，所以用 Replication 比单纯 Multicast 更稳妥，新加入客户端也能看到正确状态。

------

# 30. 实战题：多人伤害怎么实现？

流程：

```text
客户端攻击输入
    ↓
Server_Attack
    ↓
服务器验证是否能攻击
    ↓
服务器做命中检测或验证客户端命中
    ↓
服务器修改目标 Health
    ↓
Health RepNotify 到客户端
    ↓
客户端更新 UI / 播放受击表现
```

如果是 GAS：

```text
服务器 Apply Gameplay Effect
    ↓
Attribute 复制
    ↓
客户端监听属性变化更新 UI
```

------

## 面试推荐回答

> 多人伤害应该由服务器处理。客户端可以请求攻击，但服务器要验证攻击条件和命中结果，然后修改目标血量。血量通过 RepNotify 或 GAS Attribute 同步到客户端，客户端再更新 UI 和表现。不能让客户端直接决定伤害结果。

------

# 31. 第十一部分综合面试模板

如果面试官问：“你了解 UE 网络同步吗？”

可以这样回答：

> UE 多人游戏通常是客户端-服务器模型，服务器拥有权威状态。客户端负责输入和表现，关键逻辑如伤害、拾取、胜负、生成重要 Actor 等应该由服务器决定。客户端通过 Server RPC 向服务器发起请求，服务器验证后执行逻辑，再通过 Replication 或 RPC 把结果同步给客户端。
>
> Replication 用来同步状态，比如血量、分数、是否死亡、门是否打开；RPC 用来同步事件，比如攻击请求、播放爆炸特效、显示 UI。Server RPC 是客户端请求服务器，Client RPC 是服务器通知某个客户端，Multicast 是服务器通知所有相关客户端。
>
> 变量复制可以用 Replicated 或 RepNotify，RepNotify 适合在客户端收到变量变化后更新 UI 或动画。网络优化上要注意只复制必要 Actor 和变量，合理使用 Net Update Frequency、Relevancy 和 Dormancy。UI 一般只在本地 PlayerController 创建，不应该在 GameMode 中创建。

------

# 32. 简短版背诵答案

面试时可以背这个版本：

> UE 网络是客户端-服务器模型，服务器拥有权威状态。客户端负责输入和表现，关键逻辑要交给服务器，比如伤害、拾取、生成道具、胜负判断。
>
> Replication 用来同步状态，比如血量、位置、分数；RPC 用来同步事件。Server RPC 是客户端请求服务器，Client RPC 是服务器通知某个客户端，Multicast 是服务器广播给所有相关客户端。
>
> 变量复制可以用 Replicated 或 RepNotify，RepNotify 常用于客户端收到新值后更新 UI 或动画。需要同步给所有人的 Actor 应该由服务器 Spawn，并开启 Replicates。UI 一般只在本地 PlayerController 创建，不能放在 GameMode。
