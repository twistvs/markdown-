# `std::vector` 面试知识点

> 适用范围：C++11 及以后。本文讨论标准语义与主流实现；增长倍数、内部成员布局等若未被标准强制，会特别说明。

## 1. 一句话认识 `vector`

`std::vector<T>` 本质上是一个**元素连续存储、容量可动态增长的顺序容器**。

- 元素位于一段连续的动态存储中，因此支持 `O(1)` 随机访问。
- 尾部空间充足时，尾插通常是 `O(1)`。
- 容量不足时需要重新分配更大的连续空间，并搬迁全部已有元素。
- 中间插入、删除通常需要移动后续元素，因此是 `O(n)`。
- 连续布局具有良好的 CPU Cache 局部性，实际性能往往优于链式容器。

自 C++17 起，`vector::data()` 对非空容器返回首元素地址；对任意 `i < size()`，都可以认为：

```cpp
&v[i] == v.data() + i;
```

## 2. 典型三指针布局

主流实现可抽象为三个指针，但 **C++ 标准不强制实现必须真的保存三个指针**：

```cpp
template<class T, class Allocator = std::allocator<T>>
class vector {
    T* begin_;        // 已构造元素区间的起点
    T* end_;          // 已构造元素区间的终点（尾后位置）
    T* cap_end_;      // 已分配存储区间的终点
};
```

示意图：

```text
begin_                         end_                 cap_end_
  ↓                              ↓                      ↓
  +------+------+------+---------+---------+------------+
  |  T0  |  T1  |  T2  | 未构造  | 未构造  |   未构造   |
  +------+------+------+---------+---------+------------+
  |<------ size() ----->|
  |<---------------- capacity() ----------------------->|
```

概念上：

```cpp
size()     == end_ - begin_;
capacity() == cap_end_ - begin_;
```

`[begin_, end_)` 中是已经构造、可访问的 `T` 对象；`[end_, cap_end_)` 只是原始存储空间，还不是可访问的 `T` 对象。

## 3. `size` 与 `capacity`

| 概念 | 含义 | 对象是否已构造 |
|---|---|---|
| `size()` | 当前实际元素个数 | 是 |
| `capacity()` | 不重新分配内存时最多能容纳的元素数 | `size()` 以外的部分没有构造对象 |

始终满足：

```cpp
v.size() <= v.capacity();
```

示例：

```cpp
std::vector<int> v;
v.reserve(10);

// 通常：size == 0，capacity >= 10
// 不能访问 v[0]，因为元素尚未构造。
```

容量空间已经申请，并不代表其中已经存在元素。对 `size()` 以外的位置使用下标访问属于未定义行为。

## 4. 扩容机制与增长策略

当 `size() == capacity()` 时再执行尾插，典型流程如下：

1. 通过 allocator 申请一块更大的连续原始内存。
2. 在新内存中移动或拷贝构造已有元素。
3. 构造新元素。
4. 销毁旧内存中的元素。
5. 释放旧存储。
6. 更新内部指针、大小和容量信息。

### 4.1 为什么不每次只增加一个位置

如果每次容量只增加 1，第 `n` 次插入可能需要搬迁前面 `n - 1` 个元素，总搬迁量约为：

```text
1 + 2 + 3 + ... + (n - 1) = O(n²)
```

因此实现通常采用**几何增长**，例如约 `1.5` 倍或 `2` 倍，使多次尾插的总搬迁成本保持线性级别。

> **增长倍数不是 C++ 标准规定的。** 不同标准库、平台和版本可能采用不同策略，面试时不应把“必定 1.5 倍”或“必定 2 倍”说成标准结论。

### 4.2 `push_back` 为什么是均摊 `O(1)`

单次发生扩容的 `push_back` 是 `O(n)`，但扩容不会每次发生。若容量按几何倍数增长，连续插入 `n` 个元素时，总搬迁次数可由几何级数约束在 `O(n)`，因此平均到每次插入为：

```text
总成本 O(n) / n 次插入 = 均摊 O(1)
```

这里的**均摊复杂度**不是概率意义上的平均，也不表示每一次都是常数时间。

## 5. 扩容时的拷贝、移动与 `noexcept`

扩容时，`vector` 希望把旧元素移动到新内存，因为移动通常比深拷贝便宜。但标准容器还需要考虑异常安全。

典型选择逻辑可近似理解为：

- 如果 `T` 的移动构造函数是 `noexcept`，优先移动。
- 如果移动可能抛异常而 `T` 又可拷贝，通常选择拷贝，以便失败时保留原容器，维持强异常保证。
- 如果 `T` 不可拷贝且移动可能抛异常，只能尝试移动；一旦抛出，异常保证可能降低，具体受标准条款约束。

```cpp
class Widget {
public:
    Widget(const Widget&);              // 可拷贝
    Widget(Widget&&) noexcept;           // 明确承诺移动不抛异常
};
```

面试重点：**为资源管理类型正确实现移动操作，并在确实不会抛异常时标记 `noexcept`，可帮助 `vector` 在扩容时采用移动。** 不要为了性能虚假标记 `noexcept`；若异常从 `noexcept` 函数逃出，程序会调用 `std::terminate`。

常见辅助条件与 `std::move_if_noexcept` 的思想一致：

```cpp
std::is_nothrow_move_constructible_v<T> ||
!std::is_copy_constructible_v<T>
```

## 6. `push_back` 与 `emplace_back`

| 操作 | 接收内容 | 构造方式 |
|---|---|---|
| `push_back(value)` | 一个已经存在或临时的 `T` | 将该对象拷贝/移动进容器 |
| `emplace_back(args...)` | `T` 构造函数的参数 | 在尾部位置直接构造 `T` |

```cpp
struct Person {
    Person(std::string name, int age);
};

std::vector<Person> people;

Person p{"Alice", 20};
people.push_back(p);                     // 拷贝 p
people.push_back(Person{"Bob", 21});    // 通常移动临时对象
people.emplace_back("Carol", 22);        // 在 vector 尾部直接构造
```

注意：

- `emplace_back` 省掉的是“先构造临时 `T`，再移入”的潜在步骤，并非永远更快。
- 若已经有一个 `T` 对象，`push_back(std::move(obj))` 语义通常更直接。
- `emplace_back` 可能调用 `explicit` 构造函数，且完美转发会使重载选择更隐蔽；不能机械地全部替换成 `emplace_back`。
- 两者在容量不足时都可能触发扩容，并使相关迭代器、指针和引用失效。

## 7. `insert`、`erase` 与中间操作

连续存储决定了中间操作需要搬移元素：

| 操作 | 典型复杂度 | 原因 |
|---|---:|---|
| 随机访问 `v[i]` | `O(1)` | 地址可直接计算 |
| 尾部 `push_back` / `emplace_back` | 均摊 `O(1)` | 偶尔扩容搬迁全部元素 |
| 尾部 `pop_back` | `O(1)` | 销毁最后一个元素 |
| 中间 `insert` | `O(n)` | 需要后移插入点后的元素；还可能扩容 |
| 中间 `erase` | `O(n)` | 需要前移删除点后的元素 |
| 查找某个值 | `O(n)` | `vector` 本身不提供索引结构 |

`erase` 后的常见写法：

```cpp
for (auto it = v.begin(); it != v.end(); ) {
    if (should_remove(*it)) {
        it = v.erase(it);  // 返回被删元素后一个元素的新迭代器
    } else {
        ++it;
    }
}
```

批量按条件删除：

```cpp
// C++20
std::erase_if(v, [](const auto& x) { return should_remove(x); });

// C++11/14/17：erase-remove idiom
v.erase(std::remove_if(v.begin(), v.end(), pred), v.end());
```

## 8. 迭代器、指针与引用失效

这是高频面试题。核心判断是：**底层内存是否重新分配，以及元素是否发生位置移动。**

### 8.1 发生重新分配时

一旦 reallocation 发生，所有指向旧元素的：

- 迭代器；
- 指针；
- 引用；
- 旧的 `data()` 返回值；

都会失效。

```cpp
int* p = &v[0];
v.push_back(x);   // 如果触发扩容
// p 已悬空，不可解引用
```

### 8.2 未发生重新分配时

| 操作 | 失效规则（未发生 reallocation） |
|---|---|
| `push_back` / `emplace_back` | 原有元素的引用、指针、迭代器仍有效；原来的 `end()` 失效 |
| `insert(pos, ...)` | `pos` 及其之后的迭代器、指针、引用失效；之前的通常仍有效 |
| `erase(pos)` / `erase(first,last)` | 删除位置及其之后的迭代器、指针、引用失效 |
| `pop_back()` | 指向被删除元素及原 `end()` 的相关对象失效 |
| `clear()` | 所有元素均被销毁，指向元素的迭代器、指针、引用失效 |
| `reserve(n)` | 若发生 reallocation，则全部失效；否则不失效 |
| `resize(n)` | 扩容导致 reallocation 时全部失效；缩小时，被删除元素及其后的相关对象失效 |
| `shrink_to_fit()` | 若实现进行了 reallocation，则全部失效；请求未被采纳则不发生变化 |

安全实践：修改容器后，不要盲目继续使用旧迭代器；优先使用操作的返回值，或重新获取迭代器。

## 9. `reserve` 与 `resize`

| 对比项 | `reserve(n)` | `resize(n)` |
|---|---|---|
| 主要作用 | 预留至少可容纳 `n` 个元素的容量 | 把实际元素数量改为 `n` |
| 是否改变 `size()` | 否 | 是 |
| 是否可能改变 `capacity()` | 当 `n > capacity()` 时会 | 增大且容量不足时会 |
| 是否构造新元素 | 否 | 增大时会构造 |
| 是否销毁元素 | 否 | 缩小时会销毁 |

```cpp
std::vector<int> a;
a.reserve(100);  // size == 0，capacity >= 100

std::vector<int> b;
b.resize(100);   // size == 100，100 个 int 已存在并被值初始化
```

如果预计要插入大量元素，预先 `reserve` 能减少扩容次数：

```cpp
std::vector<Record> records;
records.reserve(expected_count);

for (...) {
    records.emplace_back(...);
}
```

不建议在每次 `push_back` 前都调用 `reserve(size() + 1)`，这可能破坏几何增长，使整体性能退化到 `O(n²)`。

## 10. `clear` 与 `shrink_to_fit`

### 10.1 `clear()`

```cpp
v.clear();
```

- 销毁所有元素；
- `size()` 变为 `0`；
- **通常不改变 `capacity()`，不会释放底层存储**；
- 对非平凡析构类型，需要逐个销毁元素，复杂度为线性。

保留容量是为了后续重新填充时复用内存。

### 10.2 `shrink_to_fit()`

```cpp
v.shrink_to_fit();
```

- 请求把容量收缩到接近 `size()`；
- 它是**非强制请求**，实现可以不采纳；
- 若实际发生重新分配，所有迭代器、指针和引用失效；
- 频繁收缩再增长会产生额外分配与搬迁，不应作为常规操作。

若确实需要通过临时对象尝试释放多余容量，可见到：

```cpp
std::vector<T>(v).swap(v);
```

但这会复制或移动元素并重新分配，成本明确，且也会使原有迭代器、指针和引用失效。

## 11. `vector` 对象和元素分别在哪里

```cpp
void f() {
    std::vector<int> v(1000);
}
```

- 局部变量 `v` 这个**管理对象本身**通常位于栈上，内部只保存指针/大小/allocator 状态等少量信息。
- 1000 个 `int` 所在的连续存储通常由 allocator 从自由存储区（常口语化称为“堆”）申请。
- 如果 `vector` 本身由 `new` 创建，管理对象也位于动态存储中。
- 如果 `vector` 是全局变量、静态变量或另一个对象的成员，它本身的位置由其存储期或宿主对象决定。

因此，“`vector` 在栈上还是堆上”不能笼统回答。应区分：

```text
vector 管理对象本身的位置
              ≠
vector 元素存储区的位置
```

## 12. allocator 基本原理

`std::vector<T, Allocator>` 的 allocator 负责管理元素所需的原始存储。概念上可分为：

1. `allocate(n)`：申请足以容纳 `n` 个 `T` 的未初始化存储。
2. `construct`（现代标准通常经 `std::allocator_traits` 调用）：在指定地址构造对象。
3. `destroy`：调用对象析构函数。
4. `deallocate`：释放原始存储。

```cpp
using Traits = std::allocator_traits<Alloc>;

T* p = Traits::allocate(alloc, n);           // 只有原始空间
Traits::construct(alloc, p, constructor_args...); // 对象生命周期开始
Traits::destroy(alloc, p);                   // 对象生命周期结束
Traits::deallocate(alloc, p, n);             // 释放空间
```

关键点：

- **内存分配与对象构造是两件事**。
- `capacity()` 对应已分配的槽位数量，`size()` 对应其中已构造对象的数量。
- 自定义 allocator 可用于内存池、共享内存、特定对齐、统计与调试等场景。
- allocator 的状态、传播规则和相等性会影响容器的拷贝、移动、交换行为；普通面试通常掌握基本职责即可。
- `std::pmr::vector<T>` 使用多态内存资源，适合需要在运行时选择内存资源的场景。

## 13. 与其他顺序容器的面试对比

| 容器 | 内存布局 | 大小 | 随机访问 | 尾部插入 | 中间插删 | 迭代器稳定性 | 典型适用场景 |
|---|---|---|---:|---:|---:|---|---|
| `std::array<T, N>` | 连续 | 编译期固定 | `O(1)` | 不可扩容 | `O(n)`（手动移动） | 无扩容失效 | 固定大小、可栈内嵌、零动态分配 |
| `std::vector<T>` | 连续 | 动态 | `O(1)` | 均摊 `O(1)` | `O(n)` | 扩容全部失效 | 默认首选的动态顺序容器 |
| `std::deque<T>` | 分段连续 | 动态 | `O(1)` | 两端通常 `O(1)` | 中间 `O(n)` | 规则较复杂 | 频繁两端插删、无需整段连续内存 |
| `std::list<T>` | 双向链表、节点分散 | 动态 | `O(n)` | `O(1)` | 已知位置时插删 `O(1)` | 除被删节点外通常稳定 | 需要节点稳定性、频繁拼接或已知位置插删 |

### 13.1 `vector` vs `array`

- 二者都连续存储且随机访问为 `O(1)`。
- `array` 大小编译期固定，元素直接内嵌在对象中；`vector` 大小动态，元素通常在单独的动态存储区。
- 固定规模且无需动态增长时，`array` 更简单，也避免额外动态分配。

### 13.2 `vector` vs `list`

- `vector` 连续、缓存友好、每个元素无节点指针开销；`list` 节点分散，遍历常有缓存未命中。
- `list` 在**已经拿到插入/删除位置的迭代器**时，单点插删为 `O(1)`；但找到位置仍可能是 `O(n)`。
- 不应仅凭“中间插删多”就直接选择 `list`。实际中，`vector` 的缓存优势常使它在数据规模和元素移动成本可接受时更快。
- `list` 更突出的优势是节点地址稳定以及 `splice` 等链表操作。

### 13.3 `vector` vs `deque`

- `deque` 通常由多块缓冲区加索引结构组成，并不保证所有元素整体连续。
- `deque` 支持高效头插和尾插；`vector` 头插需要整体移动。
- `vector` 可通过 `data()` 与需要连续内存的 C API、I/O、SIMD 等场景协作；`deque` 不适合直接当作一整块连续数组。

## 14. 常见陷阱

### 14.1 保存元素地址后继续插入

```cpp
auto* p = &v[0];
v.emplace_back(...);  // 可能扩容
use(*p);               // 可能使用悬空指针
```

若必须保存索引，可在修改后通过索引重新取得元素；或者预先合理 `reserve`，同时确保插入数不超过容量。

### 14.2 在范围 `for` 中修改同一个 `vector`

```cpp
for (auto& x : v) {
    v.push_back(x); // 可能使循环内部迭代器失效，行为危险
}
```

范围 `for` 背后依赖迭代器。修改容器可能使它们失效，应改用不会失效的算法或重新设计遍历过程。

### 14.3 误认为 `reserve` 创建了元素

```cpp
v.reserve(10);
v[0] = 42;          // 错误：size 仍为 0，属于未定义行为

v.resize(10);
v[0] = 42;          // 正确
```

### 14.4 `vector<bool>` 的特殊性

`std::vector<bool>` 通常是按位压缩的特化：

- 一个元素可能只占一位；
- `operator[]` 返回代理对象，不一定是 `bool&`；
- 不能把它完全当作普通 `vector<T>`；
- 若需要普通、可寻址的字节元素，可考虑 `std::vector<std::uint8_t>`；固定大小位集可考虑 `std::bitset<N>`。

## 15. 常见面试题与参考回答

### Q1：`vector` 的底层原理是什么？

**参考回答：** `vector` 是动态连续数组。典型实现维护起始、已用区尾后和容量区尾后三个指针，用它们表示 `size` 与 `capacity`。空间不足时会申请更大的连续内存，将旧元素拷贝或移动过去，销毁旧元素并释放旧内存。连续存储使随机访问为 `O(1)` 且缓存友好，但扩容会使所有指向元素的迭代器、指针和引用失效，中间插删也要移动元素。

### Q2：为什么 `push_back` 是均摊 `O(1)`？

**参考回答：** 未满时尾插是常数时间，只有容量不足才以 `O(n)` 搬迁已有元素。实现通常按几何比例增长容量，使连续 `n` 次插入的总搬迁量为 `O(n)`，所以均摊到每次是 `O(1)`。增长倍数由实现决定，不是标准固定值。

### Q3：扩容时一定用移动吗？

**参考回答：** 不一定。为了异常安全，若移动构造是 `noexcept`，通常会移动；若移动可能抛异常而类型可拷贝，通常会拷贝，以便失败后保留原数据；不可拷贝时则可能只能移动。给真正不抛异常的移动构造标记 `noexcept` 有助于容器选择移动。

### Q4：`reserve` 和 `resize` 有什么区别？

**参考回答：** `reserve` 只保证容量至少达到指定值，不改变 `size`，也不创建元素；`resize` 改变元素数量，增大时构造元素，缩小时销毁元素，必要时也会扩容。

### Q5：`clear()` 会释放内存吗？

**参考回答：** `clear` 会销毁所有元素并把 `size` 置零，但通常保留 `capacity` 以便复用。`shrink_to_fit` 可以请求收缩容量，但不是强制保证，且若重新分配会使迭代器、指针和引用全部失效。

### Q6：哪些操作会让迭代器失效？

**参考回答：** 先看是否发生重新分配，若发生则全部失效。未重新分配时，尾插通常只使旧 `end` 失效；中间插入使插入点及之后失效；删除使删除点及之后失效。实际编码中应使用操作返回的新迭代器，或修改后重新获取。

### Q7：`push_back` 与 `emplace_back` 怎么选？

**参考回答：** `push_back` 接受一个 `T` 对象并拷贝或移动到容器中，`emplace_back` 完美转发构造参数并在尾部直接构造。需要由参数直接构造元素时可用 `emplace_back`；已有 `T` 对象时 `push_back` 通常更清晰。`emplace_back` 并非必然更快，也会触发扩容和失效规则。

### Q8：为什么很多场景优先选 `vector` 而不是 `list`？

**参考回答：** `vector` 连续存储，缓存局部性好，没有每节点指针开销，随机访问还是 `O(1)`。`list` 虽然在已知位置时插删为 `O(1)`，但查找位置是 `O(n)`，节点分散也不利于缓存。除非需要稳定节点地址、频繁链表拼接或确有大量已定位的插删，否则 `vector` 往往是更好的默认选择。

### Q9：`vector` 在栈上还是堆上？

**参考回答：** 要区分管理对象和元素存储区。局部 `vector` 对象本身通常在栈上，但它管理的元素通常由 allocator 在动态存储区申请。若 `vector` 本身是成员、全局对象或动态创建对象，它自己的位置由宿主和存储期决定。

### Q10：如何减少 `vector` 扩容带来的开销？

**参考回答：** 如果能估计元素数量，提前调用一次合理的 `reserve`；让元素类型具有高效且真正 `noexcept` 的移动构造；批量插入时使用范围接口；不要在每次插入前 `reserve(size()+1)`，也不要频繁 `shrink_to_fit`。

## 16. 可直接背诵的面试回答模板

> `std::vector` 本质上是一个动态连续数组。典型实现可以理解为维护三个指针：首元素位置、已构造元素的尾后位置和已分配空间的尾后位置，因此 `size` 表示实际元素数，`capacity` 表示不扩容时最多能容纳的元素数。连续存储让它支持 `O(1)` 随机访问，并且缓存局部性很好。
>
> 当尾部空间不足时，`vector` 会申请一块更大的连续内存，把已有元素移动或拷贝到新空间，再销毁旧元素并释放旧内存。容量通常按几何比例增长，但具体是 1.5 倍还是 2 倍由标准库实现决定。单次扩容是 `O(n)`，但连续尾插的总成本是线性的，所以 `push_back` 的复杂度是均摊 `O(1)`。扩容时，如果元素的移动构造是 `noexcept`，通常优先移动；否则为了强异常安全，在可拷贝时可能选择拷贝。
>
> `push_back` 把现有对象拷贝或移动进去，`emplace_back` 用构造参数在尾部直接构造对象，但后者并非永远更快。中间 `insert` 和 `erase` 因为要搬移后续元素，通常是 `O(n)`。如果发生重新分配，所有迭代器、指针和引用都会失效；不扩容时，中间插入或删除一般会使操作位置及其之后的相关对象失效。
>
> `reserve` 只预留容量，不改变 `size`，而 `resize` 会真正改变元素个数并构造或销毁元素。`clear` 会销毁全部元素，但通常保留容量；`shrink_to_fit` 只是收缩请求，不保证一定执行。实际选型上，动态顺序存储通常优先考虑 `vector`；固定大小选 `array`，频繁两端操作可考虑 `deque`，确实需要节点地址稳定或链表拼接时再考虑 `list`。

## 17. 速记总结

```text
本质：动态连续数组
布局：典型三指针 begin / end / capacity_end
访问：随机访问 O(1)，缓存友好
尾插：均摊 O(1)，扩容当次 O(n)
扩容：几何增长，倍率由实现决定
搬迁：优先考虑 noexcept move，否则可能 copy
中间插删：O(n)
失效：reallocation 后全部失效；未扩容时看元素是否被移动
reserve：只改容量，不创建元素
resize：改变元素个数，会构造或销毁元素
clear：清元素，通常不清容量
shrink_to_fit：非强制收缩请求
位置：管理对象的位置与元素动态存储区的位置要分开回答
默认选型：大多数动态顺序场景优先 vector
```
